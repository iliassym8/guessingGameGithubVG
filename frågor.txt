Steg 5 - Skapa en textfil med svar på frågor

●Vad är pull repektive push?
git push: Används för att skicka upp sparade ändringar (commits) från din lokala dator till ett remote repository (till exempel GitHub). Det gör att andra kan se koden eller att en molnversion blir uppdaterad.

git pull: Används för att göra tvärtom. Den hämtar hem och slår ihop (merge) de senaste ändringarna från GitHub till min lokala dator. Detta är viktigt för att hålla kod synkad, särskilt om man jobbar i grupp.

●När använder man log respektive status?
git status: Används hela tiden för att se nuläget. Den visar vilka filer någon har ändrat, vilka som är tillagda (staged) och vilken branch (HEAD) någon befinner sig på just nu.

git log: Används när någon vill titta bakåt i historiken. Den visar en lista över alla tidigare commits, vem som har gjort dem, datum och commit-meddelanden. Perfekt när man letar efter när en viss bugg dök upp.

●Vad är en Git branch och varför är de viktiga?
En branch (gren) är som en separat, parallell version av ditt projekt. När du skapar en ny branch utgår den från din kod (ofta från main), men allt du gör där påverkar inte originalkoden förrän du bestämmer dig för att slå ihop det (merge). 
De är livsviktiga för att man ska kunna experimentera, testa nya funktioner eller bygga ut spelet utan att riskera att pajja den fungerande koden i main. Det gör det också möjligt för flera utvecklare att jobba på samma projekt samtidigt utan att krocka med varandra.

#git merge
När du kör git merge feature-branch skapar Git en helt ny merge commit som binder samman historiken från båda branches.

Fördelar
Säkerhet & Kontext: Historiken speglar exakt vad som hände i verkligheten och när grenarna skapades och slogs ihop.
Ingen ändrad historik: Ändrar aldrig befintliga commit-ID:n (hasher), vilket gör den väldigt säker när flera personer delar samma branch.

Nackdelar:
Suddig historik: Om det görs många merges kan historikträdet (git log) bli väldigt rörigt med massor av linjer som korsar varandra.
Många onödiga "merge branch" commits.

#git rebase
När du kör git rebase main på din feature branch flyttar du basen för din branch till den senaste commiten på main. Git kopplar tillfälligt loss dina commits, lägger på ändringarna från main, och spelar sedan in dina commits igen ovanpå.

Fördelar:
Ren och linjär historik: Historiken ser ut som en rak linje utan avstickare eller extra merge-commits. Det blir extremt lätt att läsa med git log.

Nackdelar:
Skriver om historiken: Gamla commits raderas och ersätts med nya commits som har nya commit-ID:n.
Farligt på delade branches: Om någon annan jobbar på samma branch som du rebasar skapar det stora problem. Så kanske tips är: Undvik att rebasa en delad branch.

Motivering: När använder man vad?
Varför välja git rebase?
För att städa upp din lokala feature branch innan du gör en Pull Request (PR). Det gör att historiken för hela projektet blir rak, snygg och enkel att läsa för resten av teamet utan massor av onödiga småcommits eller merge-rader.
När är git merge att föredra?
När du ska slå ihop en stor och viktig feature branch med main, eller på grenar som flera i teamet jobbar på samtidigt. Då vill man spara den exakta kontexten för när grenen slogs ihop, och man riskerar inte att förstöra historiken för andra i teamet genom att skriva om commit-ID:n.
